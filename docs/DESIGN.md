# Обзор проекта

Проект — микросервис для трекинга статусов тендеров в контексте заданий №6 и №9. Планируется **FastAPI**-сервис, который позволит создавать тендеры и управлять их статусами. Основные задачи:

- **Задание №6:** базовые операции с тендерами (создание и получение), смена статуса тендера с сохранением истории изменений.
- **Задание №9:** контейнеризация (Docker, Docker Compose) и CI (GitHub Actions) для запуска, миграций и тестирования.

- **Дополнительная AI-функция:** анализ конкретного изменения статуса через внешний LLM API. На основе данных тендера, предыдущего и нового статуса и указанной причины LLM будет формировать краткий вывод, наблюдения и рекомендации.

## Зачем здесь AI-функция?

Сухая смена статуса не информативна, есть риск утонуть в текучке. Даже без сложной логики можно хотя бы минимально увеличить информативность действия. Например, при переводе тендера в `lost` сервис сможет предложить, на что обратить внимание в похожих случаях в будущем, а при переходе в `won` — выделить потенциально полезные наблюдения.

LLM при этом не будет менять данные тендера или принимать решения за пользователя.

FastAPI-часть приложения будет использовать асинхронный подход для I/O с PostgreSQL. AI-анализ будет выполняться отдельно в фоновой задаче через очередь: API поставит задачу в Redis, а Celery worker обратится к внешнему LLM API. Благодаря этому долгий внешний запрос не будет удерживать HTTP-запрос открытым.

## Технологии

- **Python 3.12**.
- **FastAPI** как основной веб-фреймворк.
- **Pydantic** для валидации, **pydantic-settings** для конфигурации через окружение.
- **SQLAlchemy 2.x** с `AsyncSession` для ORM и асинхронной работы с БД.
- **Alembic** для миграций схемы базы данных.
- **PostgreSQL** с **psycopg 3**.
- **Redis** — брокер очередей для фоновых задач AI-анализа и backend для хранения состояния и результата задачи.
- **Celery** — выполнение фоновых задач AI-анализа.
- **Docker & Docker Compose** для контейнеризации приложения, worker, БД и Redis.
- **GitHub Actions** для CI (линтинг и тесты).
- **pytest** для тестирования.
- **Ruff** для статического анализа.

## Архитектура

Приложение будет разделено на несколько простых слоёв:

- **API** — FastAPI endpoints, принимающие HTTP-запросы и возвращающие ответы.
- **Schemas / DTO** — Pydantic-модели для входных и выходных данных.
- **Service layer** — бизнес-логика создания тендеров, смены статусов и AI-анализа.
- **Data layer** — SQLAlchemy-модели и работа с PostgreSQL через `AsyncSession`.
- **LLM integration** — отдельный модуль для взаимодействия с внешним AI-провайдером.
- **Background worker** — Celery worker для выполнения AI-анализа вне HTTP-запроса.

На каждый запрос, требующий работы с БД, через FastAPI dependency будет предоставляться `AsyncSession`. После завершения запроса сессия закрывается. Commit и rollback выполняются в соответствии с логикой конкретной операции.

Интеграция с LLM будет отделена от сервисной логики через контракт `LLMClient`, поэтому код фоновой задачи не будет зависеть от SDK конкретного провайдера.

Redis будет подключён как полноценный брокер очередей. FastAPI ставит задачу AI-анализа в очередь, Celery worker забирает её и выполняет обращение к LLM. Redis также используется как result backend: в нём временно хранится состояние задачи и результат, который затем можно получить по `task_id`.

## Модель данных

**Tender** — главная сущность:

- `id` — целочисленный PK.
- `title` — текст.
- `description` — текст.
- `status` — `ENUM('draft', 'active', 'won', 'lost')`.
- `created_at`, `updated_at` — timestamps в UTC.

**TenderStatusHistory** — история изменений статуса:

- `id` — целочисленный PK.
- `tender_id` — FK на Tender.
- `old_status` — предыдущий статус.
- `new_status` — новый статус.
- `changed_by` — строковый идентификатор автора изменения.
- `reason` — причина смены статуса.
- `changed_at` — время изменения.

Один Tender может иметь много записей в TenderStatusHistory.

Для `TenderStatusHistory.tender_id` будет создан индекс, так как получение истории конкретного тендера является одним из основных сценариев API. Дополнительные индексы **на первом этапе** не требуются.

`changed_by` **намеренно** хранится как строка: полноценная система аутентификации не входит в требования тестового задания.

## Смена статуса тендера

Статус тендера принимает четыре значения: `draft`, `active`, `won`, `lost`.

В первой версии намеренно не вводятся дополнительные правила переходов между статусами: тендер можно перевести из одного допустимого статуса в любой другой.

Единственное дополнительное ограничение — новый статус не должен совпадать с текущим. Такая операция не изменяет состояние ресурса и будет отклоняться с `409 Conflict`.

При изменении статуса сервис:

- получает Tender из БД;
- проверяет, что `new_status` отличается от текущего;
- сохраняет текущий статус как `old_status`;
- в рамках одной транзакции обновляет `Tender.status`;
- создаёт новую запись `TenderStatusHistory` с `old_status`, `new_status`, `changed_by`, `reason` и `changed_at`.

Обновление статуса и создание истории должны быть **атомарными**: либо сохраняются обе операции, либо обе откатываются.

Более строгие правила переходов, например `draft -> active -> won/lost`, если экстраполировать это на реальный проект, можно было бы добавить позже, при появлении соответствующих требований от бизнеса.

## API

Основные endpoints:

- `POST /api/v1/tenders` — создать тендер. Тело: `title`, `description`. Новый Tender получает статус `draft`.
- `GET /api/v1/tenders/{id}` — получить тендер по ID.
- `PATCH /api/v1/tenders/{id}/status` — изменить статус. Тело: `new_status`, `changed_by`, `reason`.
- `GET /api/v1/tenders/{id}/history` — получить историю изменений статуса тендера.
- `POST /api/v1/tenders/{tender_id}/history/{history_id}/ai-analysis` — поставить AI-анализ конкретного изменения статуса в очередь. При успешной постановке возвращает `202 Accepted`, `task_id` и текущий статус задачи.
- `GET /api/v1/ai-analysis/{task_id}` — получить состояние фоновой задачи и, после завершения, результат `StatusChangeAnalysis`.

Для `PATCH /status`:

- `404 Not Found` — тендер не найден;
- `409 Conflict` — `new_status` совпадает с текущим статусом;
- `422 Unprocessable Entity` — передано недопустимое значение enum или некорректное тело запроса.

Перед постановкой AI-задачи сервис проверяет, что Tender и запись истории существуют и связаны между собой. Если брокер временно недоступен, AI endpoint возвращает контролируемую ошибку, при этом основные операции с тендерами продолжают работать независимо от Redis.

Дополнительные endpoints, например список тендеров с фильтрацией и пагинацией, не входят в минимальный scope.

## Интеграция с LLM (AI-анализ)

AI-функция будет анализировать не тендер вообще, а **конкретное изменение его статуса**.

Endpoint:

`POST /api/v1/tenders/{tender_id}/history/{history_id}/ai-analysis`

При запросе сервис:

1. Получает Tender.
2. Получает запись TenderStatusHistory.
3. Проверяет, что запись истории относится к указанному тендеру.
4. Формирует `StatusChangeAnalysisInput`.
5. Ставит задачу AI-анализа в очередь Celery через Redis.
6. Возвращает `202 Accepted` с `task_id`.

Долгий запрос к внешнему LLM API выполняется уже в Celery worker. Состояние и результат задачи временно хранятся в Redis и доступны через:

`GET /api/v1/ai-analysis/{task_id}`

В `StatusChangeAnalysisInput` предполагается передавать только необходимый контекст:

- `title`;
- `description`;
- `old_status`;
- `new_status`;
- `reason`.

Результат `StatusChangeAnalysis` будет содержать:

- `summary` — краткий вывод по изменению;
- `observations` — наблюдения на основе переданного контекста;
- `recommendations` — рекомендации для похожих ситуаций в будущем.

LLM не должна представлять свои выводы как достоверное объяснение причины победы или проигрыша. Если доступного контекста недостаточно, результат рассматривается как набор гипотез и рекомендаций.

Для отделения фоновой задачи от конкретного AI-провайдера будет использоваться `Protocol`:

```python
class LLMClient(Protocol):
    def analyze_status_change(
        self,
        data: StatusChangeAnalysisInput,
    ) -> StatusChangeAnalysis:
        ...
```

Конкретная реализация, например `OpenAILLMClient`, будет соответствовать этому контракту без обязательного наследования.

FastAPI и работа с PostgreSQL остаются асинхронными. Сам вызов LLM выполняется в отдельном Celery worker, поэтому он не блокирует обработку HTTP-запросов и не требует держать SQL-транзакцию открытой.

ORM-модели напрямую в LLM-клиент передаваться не будут: в очередь передаются сериализуемые данные `StatusChangeAnalysisInput`.

Ошибки внешнего провайдера не откатывают изменение статуса. Неуспешная AI-задача получает состояние `failed`, которое можно увидеть при запросе результата по `task_id`.

## Транзакции и согласованность

Смена статуса Tender и создание TenderStatusHistory выполняются в рамках одной SQLAlchemy-транзакции через `AsyncSession`.

Главное требование:

- если статус изменён, запись истории обязательно должна существовать;
- если запись истории создать не удалось, изменение статуса не должно сохраняться.

AI-анализ не входит в эту транзакцию.

После успешного сохранения изменения статуса пользователь может отдельно поставить AI-анализ в очередь. FastAPI только создаёт задачу, а вызов LLM выполняется Celery worker. Это позволяет не держать SQL-транзакцию открытой во время сетевого запроса и не связывать успешность основной бизнес-операции с доступностью LLM или очереди.

Если AI-провайдер или Redis временно недоступны, Tender и TenderStatusHistory остаются без изменений.

## Окружение (Docker)

Для воспроизводимого окружения и контейнеризации используется Docker Compose.

Планируются четыре сервиса:

- **app** — FastAPI + Uvicorn;
- **worker** — Celery worker для фонового AI-анализа;
- **db** — PostgreSQL;
- **redis** — Redis как broker и result backend для Celery.

Приложение будет доступно на порту `8000`.

Локальный запуск:

```bash
docker compose up --build
```

Перед запуском приложения схема БД должна быть приведена к актуальной версии:

```bash
alembic upgrade head
```

Способ запуска миграций — вручную или через entrypoint — будет определён при реализации инфраструктурной части.

Redis включён в Docker Compose именно как брокер очередей, как указано в задании №9. FastAPI-приложение ставит в него задачи AI-анализа, а отдельный Celery worker получает и выполняет их. Redis также используется как result backend для временного хранения состояния и результата задачи.

## CI (GitHub Actions)

GitHub Actions workflow будет выполнять:

- проверку кода через Ruff;
- запуск pytest;
- интеграционные тесты с PostgreSQL.

Workflow будет запускаться при push и Pull Request.

Автоматический deployment в текущий scope не входит.

## Тестирование

План тестов через pytest:

- создание тендера и проверка начального статуса;
- получение тендера по ID;
- `404`, если Tender не существует;
- успешная смена статуса;
- создание TenderStatusHistory после смены статуса;
- корректность `old_status`, `new_status`, `changed_by` и `reason`;
- `409 Conflict` при попытке установить текущий статус;
- `422 Unprocessable Entity` для недопустимого значения статуса;
- проверка атомарности: при ошибке сохранения истории статус Tender не меняется;
- получение истории статусов;
- успешная постановка AI-анализа в очередь и ответ `202 Accepted` с `task_id`;
- проверка данных, переданных в `StatusChangeAnalysisInput`;
- `404`, если Tender или TenderStatusHistory не найдены;
- `404`, если запись истории не относится к указанному Tender;
- получение состояния незавершённой AI-задачи;
- получение `StatusChangeAnalysis` после успешного выполнения задачи;
- unit-тест Celery task с fake/mock `LLMClient`;
- корректное состояние `failed` при ошибке внешнего LLM;
- недоступность Redis не влияет на создание, получение и смену статусов тендера.

Интеграционные тесты будут выполняться с PostgreSQL, а не SQLite, чтобы тестовая среда соответствовала целевой СУБД.

## Git Flow

До начала разработки в `main` находятся только базовые файлы:

- `README.md`;
- `docs/DESIGN.md`;
- `LICENSE`;

Функциональность будет разрабатываться в отдельных feature-ветках и попадать в `main` через Pull Request.

Предполагаемая схема:

1. `feature/tender-tracker` — задача №6: Tender, история статусов и основное API.

## Упрощения и допущения

- `changed_by` передаётся как строка без полноценной аутентификации и авторизации.
- Модель Tender ограничена базовыми полями: сумма, дедлайн, заказчик и другие данные пока не добавляются.
- Дополнительная state machine для статусов отсутствует; запрещён только переход в уже установленный статус.
- Redis используется как broker и result backend для Celery. Основные операции с тендерами и историей статусов от Redis не зависят.
- AI-анализ вызывается пользователем отдельно и не запускается автоматически после смены статуса.
- Результат AI-анализа не сохраняется в PostgreSQL: он временно доступен через result backend Celery.
- FastAPI и работа с PostgreSQL используют асинхронную модель; LLM-запрос выполняется отдельно в Celery worker.
- Если Tender или связанная запись истории не найдены, API возвращает `404 Not Found`.
